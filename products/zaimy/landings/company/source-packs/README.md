# Source packs для МФО

В этой папке хранятся проверенные данные для карточек организаций. Для каждой МФО создаётся один Markdown-файл с таблицами, редакционными блоками и использованными источниками. Сырой текст сайтов, документов и отзывов в source pack не сохраняется.

## Структура

```text
source-packs/
  README.md
  collection-prompt.md
  template.md
  organizations/
    <organization-slug>.md
    <organization-slug>-final.md
```

## Роли файлов

- `../final.md` — единственная утверждённая спецификация, контракт данных и промпты сборщика, редактора и аналитика отзывов.
- `collection-prompt.md` — обезличенный готовый промпт для запуска сбора новой организации; перед использованием в нём заменяются бренд и slug.
- `template.md` — канонические названия, порядок разделов и полей готового source pack.
- `organizations/<organization-slug>.md` — зарезервированный или находящийся в работе source pack конкретной организации.
- `organizations/<organization-slug>-final.md` — полностью собранный, проверенный и одобренный source pack. Для структурной и редакционной сверки используются `organizations/lime-zaim-final.md`, `organizations/webbankir-final.md` и `organizations/moneyman-final.md`; они не являются источниками фактов для других МФО и не заменяют правила спецификации. Их существующие разделы отзывов также не служат эталоном актуальной выборки.

Пустой файл без суффикса `-final` означает, что для организации зарезервирован целевой путь, но сбор ещё не начат. Суффикс `-final` добавляем только после завершения всех предусмотренных этапов и финальной проверки по `../final.md`.

Приоритет при расхождениях: `../final.md` определяет смысл и правила, `template.md` — структуру результата, три готовых примера — только оформление и уровень детализации подтверждённых значений. При повторном анализе отзывов прежние параметры выборки и выводы из примера не переиспользуем.

## Локальный кэш реестра СРО

Один и тот же официальный снимок реестра СРО повторно не скачиваем для каждой МФО. Локальную копию храним в игнорируемой Git-папке `tmp/source-packs/sro/`, а в имя включаем СРО и официальную дату снимка. Перед использованием проверяем на официальной странице реестра, что дата или версия и прямой URL не изменились. Новый снимок заменяет старый; кэш без подтверждаемого происхождения не используем.

Кэш не является источником и не добавляется в Git. В каждом source pack сохраняем официальные название, дату и URL использованного реестра Tier 1.

## Рабочий порядок

1. В `collection-prompt.md` заменяются `{{БРЕНД}}` и `{{SLUG}}`, после чего промпт передаётся сборщику.
2. Сборщик проверяет обязательные источники по `../final.md` и перед загрузкой реестра СРО проверяет подходящий актуальный снимок в локальном кэше.
3. После успешной проверки поэтапно заполняет `organizations/<organization-slug>.md` на основе `template.md`, используя три одобренных `*-final.md` только как примеры оформления.
4. Готовую фактическую базу проверяет по критериям спецификации.
5. Редактор готовит описание и FAQ, а после явного одобрения пользователя добавляет их в тот же файл.
6. Аналитик независимо готовит обзор отзывов строго по разделу «Промпт обзора отзывов» в `../final.md`. До изменения source pack он показывает предусмотренную спецификацией проверку выборки, выбранный результат, готовый блок и строку источников; после одобрения добавляет только публичный блок и строку по `template.md`. README не дублирует рабочий период, числовые пороги, очистку выборки, расчёт тональности и подготовку списков похвалы и жалоб: их единственным источником остаётся `../final.md`.
7. После каждого этапа сохраняет и отправляет изменения в Git.
8. После завершения всех предусмотренных этапов проверяет целостность по `../final.md` и `template.md`, затем сверяет структуру и уровень детализации с тремя одобренными `*-final.md`.
9. Только после успешной проверки переименовывает файл в `<organization-slug>-final.md` и отправляет переименование в Git.
10. Передача в админку не входит в сбор source pack и выполняется только как отдельная задача по явной команде пользователя.
